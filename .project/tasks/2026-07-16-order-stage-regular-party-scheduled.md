**Date:** 2026-07-16
**Prompt:** "before charge the order first get confirmed by user and pos is used for walk in and order can be regular or party order or scheduled order how that is going to be handled" — scoped via two rounds of AskUserQuestion: (1) confirmation should be a true Order stage before Invoice (not just a customer-facing review), order types distinguished by timing + fulfillment + pricing; (2) Regular walk-in orders should also flow through the new Order → confirm → charge pipeline rather than keeping the old one-step Charge untouched, so the whole system is unified.

## What was done

Researched the existing Reservations/KOT/PriceLevels/Seating modules first (confirmed: no existing Order concept, `Reservation` is pure table-booking with no items/pricing, `Kot.orderId` is an already-loose unvalidated uuid, `Invoice.status` had a dead unused `DRAFT` value). Planned via EnterPlanMode/ExitPlanMode (plan at `~/.claude/plans/swift-sniffing-pizza.md`), then implemented in 9 tracked steps:

- **Extracted shared pricing logic**: `SalesService.create()`'s ~70-line price-level/GST resolution block moved into `PriceLevelsService.resolveLineItems(items, customerId?)`, reused by both `SalesService.create()` and the new `OrdersService.create()` so orders and invoices price identically. Required adding `CustomersModule` to `PriceLevelsModule`'s imports (one-directional, no cycle).
- **New `apps/api/src/orders/` module**: `Order`/`OrderItem` entities (`OrderType` regular/party/scheduled, `FulfillmentMethod` dine_in/takeaway/delivery, `OrderStatus` pending_confirmation → confirmed → billed, or cancelled). `OrdersService`: `create()` (validates scheduledFor required for party/scheduled; auto-creates a `Reservation` via the existing `ReservationsService` when a table is held for a future party/scheduled slot; occupies the table immediately instead for regular dine-in), `confirm()` (regular orders auto-fire the KOT on confirm via `sendToKitchen()`; party/scheduled don't), `sendToKitchen()` (explicit action, once per order), `charge()` (converts `discountPercent` to a flat amount and calls the *existing* `SalesService.create()` unchanged, passing the new `orderId` field), `cancel()` (cancels any already-sent KOT, releases table/reservation, guarded against cancelling billed/already-cancelled orders — no stock/accounting reversal needed since nothing was posted until charge). New `POST /orders`, `/confirm`, `/send-to-kitchen`, `/charge`, `/cancel`, `GET /orders`, `/:id`, permission-gated (`orders.charge`/`orders.cancel` added to seed; `orders.create/read/update/delete` were already auto-generated).
- **`Invoice.orderId`** (nullable) added so `SalesService.cancel()`'s existing KOT lookup keeps working (`invoice.orderId || invoice.id` — falls back to the old direct-invoice behavior for any invoice not created via an Order).
- **Frontend**: rebuilt `apps/restaurant-ui/src/modules/orders/pages/OrdersPage.tsx` (was 100% static mock data) with real `getOrders`/`confirmOrder`/`sendOrderToKitchen`/`chargeOrder`/`cancelOrder` — type/status badges, contextual per-status action buttons, a detail drawer, and a payment-method picker for charging. `POSDashboard.tsx` gained an Order Type selector (Walk-in/Party/Scheduled) — Walk-in keeps the exact same one-click Charge UX (now internally `createOrder → confirmOrder → chargeOrder` in sequence, invisible to the cashier); Party/Scheduled reveal scheduled-time/party-size/discount fields and swap the Charge button for "Place Order" (create + confirm only, no payment), with a success banner pointing to the Orders page.

## Outcome

Verified end-to-end via curl: regular order create→confirm (KOT auto-fires)→charge produced a correctly-linked Invoice with matching `orderId`/`invoiceId` cross-references; party order with a table + 10% discount correctly created a `Reservation` holding that table, did **not** auto-fire the KOT on confirm, fired it only on explicit send-to-kitchen, and charged with the exact discount amount applied. Cancellation before charge correctly cancelled the KOT and rejected double-cancel/charge-after-cancel attempts (400s with clear messages). Playwright pass: walk-in flow is pixel-identical to before (one Charge click → payment method → receipt), party order placement and the resulting Orders page listing (with working Send to Kitchen / Charge actions) both render and function correctly — zero console/network errors throughout. Both apps typecheck clean (only the two long-standing pre-existing spec-file errors remain, unrelated to this work).

Known deliberate scope limits, not bugs: no cron/scheduled auto-firing of KOTs by time (Party/Scheduled always require an explicit "Send to Kitchen" click); no per-line custom price override for party orders (one order-level `discountPercent` only); the existing Reservation table-conflict check is still not true interval-overlap logic (flagged during research, pre-existing, unrelated to this feature — not touched).
