**Prompt:** "if someone wants to cancel the order after billing or want to change any meal then what is the way give me the plan" — presented three options (cancel+recharge / in-place amendment / Credit Note), user picked Credit Note for post-serve corrections, with per-line "restore stock" toggle and combined credit+replacement in one flow (both scoped via AskUserQuestion).

## What was done

- **New `CreditNote`/`CreditNoteItem` entities** (`apps/api/src/sales/entities/credit-note.entity.ts`), registered on `SalesModule`. Added `CREDIT_NOTE` to `JournalSourceType`.
- **`SalesService.createCreditNote(invoiceId, dto)`**: validates each requested line against the invoice's original `InvoiceItem` and a running total of *already-issued* credit for that line (query-summed across non-cancelled credit notes) to prevent over-crediting; computes the credited taxable/CGST/SGST/total from the invoice's original unit price (not current live price); restores stock per-line only when requested (mirrors `cancel()`'s recipe-or-direct branching via `RecipesService.reverseOnSale`/`InventoryService.adjustStock(ADJUSTMENT_IN)`); posts a reversing journal entry (Debit Sales Revenue + GST Payable, Credit whichever account the original sale debited — Cash/Bank/Accounts Receivable based on the invoice's payment method); optionally rings up a replacement invoice by calling the existing `create()` method directly, linking it back via `CreditNote.replacementInvoiceId`.
- **Endpoints**: `POST /sales/:id/credit-notes`, `GET /sales/:id/credit-notes`, gated behind a new `sales.credit-note` permission (added to seed's `EXTRA_PERMISSIONS` and the cashier role).
- **Frontend**: `CreditNoteDialog.tsx` (per-item credit-quantity input + restore-stock checkbox, reason field, a replacement-item picker with its own payment-method selector), wired into `SalesPage.tsx` as a new "Credit Note" row action (hidden only once an invoice is cancelled). New `apps/restaurant-ui/src/modules/sales/api/sales.api.ts` for the typed API calls.
- **Bug caught while building this**: `useQuery`'s `onSuccess` callback was used to seed local form state from the fetched invoice — this project is on `@tanstack/react-query` v5, which removed that callback entirely (it would have silently never fired). Fixed with a `useEffect` keyed on the query result instead.

## Outcome

Verified end-to-end via curl: charged a 2-unit invoice, credited 1 unit with stock restore + a same-flow replacement item — ledger deltas matched exactly (Cash Account, Sales Revenue, and GST Payable all moved by precisely the credit/replacement amounts, including the replacement's own round-off), stock ended up net-correct, and the over-credit guard correctly allowed crediting the second (last remaining) unit but rejected a third attempt with a clear message. Playwright pass through the actual UI (open dialog → fill quantity/reason → post) showed zero console/network errors and the correct "CN-000003 posted, ₹313.95 credited" result.

Also fixed two bugs reported mid-session on code shipped earlier today: the receipt Print button did nothing (Tailwind's `print:hidden` was mistakenly on the dialog wrapper that contained the printable content, plus the dialog being nested inside the app's scrollable layout meant the CSS visibility trick couldn't correctly position it even after that fix — resolved by portaling `ReceiptDialog` to `document.body`), and the Charge modal only exposed Card/UPI even though the backend already supported Cash/Online/Credit — all 5 are now selectable.
