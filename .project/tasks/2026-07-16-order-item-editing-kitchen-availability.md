**Date:** 2026-07-16
**Prompt:** "if cancelled order then its invoice" — clarified through two rounds of AskUserQuestion into three concrete requirements: (1) items can be freely cancelled/swapped on an order any time before it's charged, even after being sent to kitchen; (2) kitchen staff can flag a KOT item as "unavailable" in real time, purely as a notification (not an automatic order change); (3) cancelling an Invoice from Sales should sync the status back onto its originating Order (kept as a separate action from cancelling the Order directly, which stays blocked once billed).

## What was done

- **Order item editing**: `OrdersService.updateItems(id, items)` (`PATCH /orders/:id/items`) — allowed any time the order is `pending_confirmation` or `confirmed` (i.e. right up until charge, matching "even if booked/sent to kitchen it can still be swapped"). Reuses `PriceLevelsService.resolveLineItems()` to reprice, recomputes totals against the order's existing `discountPercent`. If the order had already been sent to kitchen (`kotSent`), a **supplementary KOT** is fired for the revised full item list rather than trying to diff/edit the original ticket — KOTs are treated as immutable historical records once printed.
- **Kitchen item availability flag**: `KotItem` gained `isUnavailable`/`unavailableNote`. New `KotService.setItemAvailability()` (`PATCH /kots/:kotId/items/:itemId/availability`) is purely advisory — it does not touch order/invoice state. `KotService.findByOrderId()` was missing `relations: { items: true }` (caused a 500 the first time this was exercised) — fixed at the source since other callers only used `.id`/`.status`, so eager-loading items there is safe everywhere.
- **Surfacing to staff**: `OrdersService.findByIdWithFlags()` / `findAll()` now attach `unavailableItems: { itemName, note }[]` by querying linked KOTs — shown as a red badge on the Orders table row and a full warning banner in the order detail drawer, so staff see it before charging without anything being silently changed.
- **Cancel-sync fix**: `SalesService.cancel()` now updates the linked `Order.status` to `cancelled` when `invoice.orderId` is set (previously the Order stayed stuck showing "billed" forever after its invoice was cancelled). Implemented by injecting `Repository<Order>` directly into `SalesService` (registering the `Order` entity in `SalesModule`'s `TypeOrmModule.forFeature`) rather than importing `OrdersModule` — avoids a circular module dependency, since `OrdersModule` already imports `SalesModule` the other direction.
- **Frontend**: KOT Board gets a small flag/unflag control per item (prompts for a note, shows a struck-through red row with the note underneath). Orders page shows the warning badge/banner and a new inline item editor in the detail drawer (quantity inputs, remove, add-item picker, Save/Cancel) gated to the same pre-charge statuses as the backend guard.

## Outcome

Verified end-to-end via curl: item swap before confirming recalculated totals correctly; swapping after `kotSent=true` correctly fired a second, clearly-labeled KOT ticket rather than mutating the first; marking a KOT item unavailable surfaced immediately on `GET /orders/:id` with the exact note text; the over-credit-style guards all rejected correctly (editing a billed/cancelled order, double-flagging, etc.); cancelling an invoice correctly flipped its linked order from `billed` to `cancelled`. Playwright pass across the KOT board (flag → struck-through row + note rendered) and Orders page (edit-items flow: changed quantity from 1→3, saved, total recalculated to exactly ₹1099.35) — zero console/network errors throughout. Both apps typecheck clean.
